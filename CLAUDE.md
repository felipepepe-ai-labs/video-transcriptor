# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Architecture

Video Transcriptor EN → ES: a two-process app with no shared build.

```
Frontend (React 19 + Vite, :5173) → Backend (FastAPI, :8000) → SSH → 192.168.1.60 (Whisper large-v3-turbo, Piper TTS)
                                                                              ↓                    ↓
                                                                    MyMemory Translate API   Ollama (qwen3.6:27b, EN→ES fallback)
                                                                       (EN→ES, primary)
```

- **`backend/app.py`** holds only the FastAPI routes and the background worker (`run_transcription_job`) that drives one job through `uploading → transcribing → translating → voicing → dubbing → splitting → done`. It reuses `parse_srt`, `assign_chapters`, `ts_to_seconds`, `seconds_to_ts` (kept here, unchanged in behavior). Narration, dubbing, and chapter-splitting are best-effort bonuses on top of transcript+translation: a failure in any of them (`TTSFailed`/`dub.DubbingFailed`) is recorded on the job result (`*_error` fields) but never fails the job.
- **`backend/remote.py`** — `RemoteWhisper` wraps the whole paramiko SSH lifecycle for one job: connect (mapping both `paramiko.SSHException` and `OSError`/`NoValidConnectionsError` to a single `RemoteUnavailable`), a pre-flight disk check on remote `/tmp` (`InsufficientRemoteStorage` if free space < file size × `REMOTE_DISK_SAFETY_MARGIN`), upload, `run_transcribe()` (runs `python3 -m whisper --task transcribe`, `TranscriptionFailed` on non-zero exit or missing SRT), `run_tts_batch()` (runs Piper over the same SSH connection to synthesize one WAV per translated segment, chunked to amortize Piper's model-load cost, `TTSFailed` on failure), and a guaranteed `cleanup()` (`rm -f`/`rm -rf` of every uploaded file + output dir) called from the worker's `finally` on every exit path. There is no `run_translate()` — Whisper's `--task translate` only ever translates speech INTO English, so it cannot serve as an EN→ES path.
- **`backend/translate.py`** — `Translator` protocol with `MyMemoryTranslator` (primary; retries with backoff, batches segments under MyMemory's ~500-char query cap) and `OllamaTranslator` (fallback; batch-translates via a numbered-list prompt against a local/remote Ollama model, degrading to one segment at a time if the batch response doesn't parse cleanly). `translate_with_fallback()` tries MyMemory first, then Ollama, then gives up and returns the untranslated text (`provider` = `"untranslated"`) rather than failing the job — the provider actually used is always recorded (`result.translation_provider`), so a degraded translation is never silent.
- **`backend/dub.py`** — builds the Spanish narration track and dubbed video, all locally via `ffmpeg`/stdlib `wave` (only the TTS synthesis itself runs remotely, via `RemoteWhisper.run_tts_batch()`). `build_narration_track()` lays out per-segment Piper clips sequentially with silence gaps sized to each subtitle's timestamp — segments are not time-stretched to fit their slot, so a long segment pushes the rest of the track forward rather than overlapping audio. `mux_audio_into_video()` muxes that track onto the original video (video stream copied, audio re-encoded to AAC). `split_video_by_chapters()` cuts the dubbed video into one clip per chapter. Any `ffmpeg` failure raises `DubbingFailed`.
- **`backend/youtube.py`** — yt-dlp boundary (its own module, like `remote.py` for SSH, so tests fake it at one seam): `download_video(url, dest_path)` downloads a YouTube video as MP4 capped at 1080p directly into `uploads/{job_id}.mp4` (same naming contract as uploads, so retts/chapter reruns keep working) and returns `{title, duration, chapters}` — the video's own chapter markers, already in `assign_chapters()` shape. Any yt-dlp failure raises `DownloadFailed`. The YouTube worker (`run_youtube_job`) then drives the regular pipeline with whisper language **auto-detection** (`source_language=None`): an English video runs the full translate+dub pipeline, while a video detected as Spanish keeps its transcript as-is (`text_es = text_en`, `translation_provider = "source-es"`) and skips narration/dubbing entirely — nothing to translate, and re-voicing Spanish over Spanish is pointless. Jobs carry `source` (`"upload"`/`"youtube"`), `title`, and `url` columns so the history view can distinguish them; user-supplied chapters always win over the video's own markers.
- **`backend/jobs.py`** — SQLite-backed job store (`backend/jobs.db`, stdlib `sqlite3`) with `create_job`/`update_job`/`get_job`/`list_jobs`/`delete_job`. Survives the dev server's `reload=True` restarts, unlike an in-memory dict.
- **`backend/retranslate_job.py`** — one-off maintenance script (not imported by the app) to re-translate a job's stored segments in place when `translation_provider` shows a degraded/broken result, e.g. jobs produced before the Whisper-translate fallback was replaced with Ollama. Tracks per-segment progress via a `retranslated` marker so a long run against Ollama is resumable and inspectable mid-flight.
- **`backend/diarize.py`** — multi-speaker diarization + per-speaker gender detection, used to pick a male/female Piper voice per speaker instead of one fixed voice for the whole video. **Not yet wired into `app.py`/`run_transcription_job`** — it's a standalone module with its own unit tests (`test_diarize_unit.py`) but nothing currently imports or calls it from the live pipeline. `run_diarization(segments, remote, video_path)` is the intended entry point: it tries pyannote.audio v4 first (`try_install_pyannote()` installs it into a throwaway venv on the *remote* box on demand — not a local dependency — then `run_pyannote_diarization()` runs speaker-embedding diarization and maps speakers back to subtitle segments via word-level timestamp overlap), and falls back to `compute_pitch_per_segment()` + `cluster_pitches()` (gap-heuristic k-means over mean F0 per segment, computed on the remote box via torchaudio) when pyannote is unavailable, errored, or found only one speaker. Either path ends in `classify_genders()`/`_mean_f0_to_gender()` (male <165Hz, female >180Hz, else unknown by voice-science convention) and `resolve_voice_for_gender()` (maps a segment's gender to the `"male"`/`"female"` Piper preset, falling back to the user's originally selected voice when gender is unknown). Every entry point degrades silently on failure — segments are returned without `speaker_id`/`gender` and the existing single-voice pipeline behaves unchanged.
- **`backend/x_bookmarks.py`** + **`backend/x_sync.py`** — an X (Twitter) bookmarks curator bolted onto the app, unrelated to the transcription pipeline (adapted from a standalone `x-bookmarks-curator` project). `x_bookmarks.py` owns a separate SQLite store (`X_BOOKMARKS_DB` env var, defaults to a path under the OS tempdir — deliberately *not* NFS, to avoid SQLite locking issues) with CRUD (`sync_bookmarks`/`list_bookmarks`/`get_bookmark`/`set_interesting`/`mark_downloaded`/`mark_transcribed`/`delete_bookmark`) and its own migration shim (`_migrate()` adds new columns on startup). `x_sync.py` handles auth + scraping: `import_cookies()` parses a Netscape `cookies.txt`, requires the `auth_token`/`ct0`/`twid` X auth cookies, and writes a Playwright `storageState` JSON (plus a chmod-0600 copy of the cookies) to `X_DATA_DIR` (default `backend/data/x-bookmarks/`); `sync_x_bookmarks()` then launches headless Chromium with that session, scrolls `x.com/i/bookmarks` until content height is stable, and scrapes tweets via DOM `data-testid` selectors. `download_video()` pulls a bookmarked tweet's video via yt-dlp (already a pipeline dependency). Bookmarked videos can then be transcribed through the *same* remote Whisper connection as the main pipeline (`_transcribe_bookmark_worker`), independent of `jobs.py`/`jobs.db`.
- Chapter markers (optional, user-supplied `chapters_json` on upload) are matched to transcript segments by nearest-preceding timestamp in `assign_chapters()`.
- Endpoints: `POST /jobs` (multipart: `video` file + optional `chapters_json` + optional `voice` = `"male"`/`"female"`, default `"male"`) enqueues a job and returns `{job_id, status}` immediately. `POST /jobs/youtube` (form: `url` + same optional `chapters_json`/`voice`) does the same for a YouTube URL, adding a `downloading` stage before `uploading`. `GET /jobs` lists all jobs. `GET /jobs/{id}` returns the job's `status`/`stage`/`error`/`result`. `DELETE /jobs/{id}` removes the job row and its local audio/video artifacts. `GET /jobs/{id}/audio` / `GET /jobs/{id}/video` / `GET /jobs/{id}/chapters/{index}/video` stream the narration WAV, dubbed MP4, and per-chapter clips respectively (404 if that stage didn't complete). `GET /health` reports remote host/model config.
- X bookmarks endpoints (all background-task-driven, mirroring the async-job pattern): `POST /x/import-cookies` (multipart cookies.txt upload), `POST /x/sync` (kicks off the headless scrape), `GET /x/bookmarks` (optionally filtered by `status`), `PATCH /x/bookmarks/{id}/interesting` (toggles `new`↔`interesting`), `DELETE /x/bookmarks/{id}`, `POST /x/bookmarks/{id}/download` (yt-dlp), `POST /x/bookmarks/{id}/transcribe` (reuses the remote Whisper connection).
- Config (`REMOTE_HOST`, `REMOTE_USER`, `REMOTE_MODEL`, `REMOTE_DEVICE`, `REMOTE_DISK_SAFETY_MARGIN`, `FRONTEND_ORIGIN`, `OLLAMA_URL`, `OLLAMA_MODEL`, `MYMEMORY_EMAIL`) all come from `os.getenv` with the previous hardcoded values as defaults. X bookmarks add `X_BOOKMARKS_DB` and `X_DATA_DIR`.
- **`backend/config.py`** — `DATA_ROOT` (default `backend/`) is the root of every *media* directory: `uploads/`, `audio/`, `video/` and `x-downloads/`. The SQLite databases and the X credentials deliberately do **not** hang off it: SQLite cannot lock over a network share (this project's own NAS mount refuses to open `jobs.db` at all) and `DATA_ROOT` is meant to point at exactly that kind of disk, so they keep `JOBS_DB_PATH`/`X_BOOKMARKS_DB`/`X_DATA_DIR`. `LOG_LEVEL` (default `INFO`) drives backend logging; `DEBUG` adds the per-round scroll trace of the X scrape.
- **`frontend/src/App.jsx`** is a single-component React app: upload UI submits to `POST /jobs`, then polls `GET /jobs/{id}` every ~2s rendering the current stage until `done`/`failed`; same EN/ES tab toggle and `.srt` export as before. Calls the backend via `VITE_API_URL` (set in `frontend/.env`). A third input-mode tab (`inputMode === "x"`) renders `frontend/src/XBookmarks.jsx`, a separate component driving the `/x/*` endpoints (refresh/sync, mark interesting, download, delete) — it doesn't share state with the transcription job UI beyond living in the same page.
- There is no auth beyond CORS restricted to `FRONTEND_ORIGIN`, and no persistence beyond `backend/uploads/`, `backend/audio/`, `backend/video/`, `backend/jobs.db`, and (for X bookmarks) `backend/data/x-bookmarks/` + the bookmarks SQLite DB (local scratch, cleaned up remotely but not locally) — treat this as a personal utility tool, not a multi-user service.

## Commands

```bash
# Backend — from backend/
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python app.py                    # → http://localhost:8000 (reload=True)

# Frontend — from frontend/
npm install
npm run dev                      # → http://localhost:5173
npm run build
npm run lint                     # oxlint
```

Backend tests: `cd backend && source .venv/bin/activate && pytest -v` (`backend/tests/test_jobs_e2e.py`, SSH boundary mocked). No test suite exists for the frontend.

## Requirements

- Backend: Python 3.12+, and passwordless SSH key auth to `felipe@192.168.1.60` (the remote box must already have `whisper` installed and a GPU available).
- X bookmarks sync additionally needs Playwright's Chromium installed locally: `playwright install chromium` (the backend raises a clear `ScrapingError` if it's missing rather than failing obscurely).
- Frontend: Node 22+.
